# 技能 2：入库即反查（reverse-lookup）

## 用途

新档案入**库**的那一瞬间，回答三个问题：库里有没有**同类尝试**？有没有**冲突判断**？
还缺哪些信息才能定性？（对应设计约束：入库当下反查，而不是等人想起来再搜。）

## 什么时候用

- 一条新档案刚抽出来、准备入库时；
- 用户说「这条以前是不是做过」「有没有冲突的结论」「还缺什么」。

## 输入

- 必填：待入库的档案（或它的关键词）。
- 必填：库文件。

## 步骤

1. **召回候选**（确定性，宁少不凑——返回空说明真的没有，不要硬找）：

```bash
python3 bin/rra_cli.py recall <库文件> "<阻塞点或关键观察>" --limit 5
```

2. **逐条判定关系**（语义，你来做）：对每个候选给出 `重复` / `相似` / `冲突`，并写进
   `links[]`，其中：
   - `target`：候选档案编号；
   - `same` / `diff`：相同点与不同点，**必须是可核对的具体条件**（维度值、精度、硬件等）；
   - `transferable`：这条经验在什么条件下可以迁移过去；没有就写空，不要硬编。

3. **写 `missing_info`**：只写「补上就能定性」的信息，按重要性排序，一次问最关键的几条。
4. **澄清往返**：用户答完后记账（确定性）：

```bash
python3 bin/rra_cli.py apply-clarification <档案.json> "<已澄清的字段1>" "<字段2>"
```

   该命令会移除已澄清项并把 `version` 递增——**最终确认的那一版才是入库版本**，别手工改版本号。

5. **冲突要给出判定依据**：若判为 `冲突`，必须同时指出「两侧的哪些条件不同」，
   必要时先跑技能 3（条件对比）；条件不足时结论写「条件不全」，不要下判决。

## 输出

- 更新后的档案 JSON（含 `links`、`missing_info`、递增后的 `version`）。
- 中文说明：命中了谁、关系是什么、依据是哪句原文、还缺什么。

## 拒绝条件（必须照做）

- `recall` 返回空 → 明说「库内无同类记录」，不要用你自己的联想补一个"相似记录"。
- 候选记录只有一个共同词、却不共享任何条件维度 → 不得判为 `相似`，最多写「疑似，条件不足」。
- 不许把 `assumption` 当成冲突依据；冲突必须落在可核对的条件差异上。
