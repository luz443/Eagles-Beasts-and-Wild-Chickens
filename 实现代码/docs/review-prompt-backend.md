## 0. 一句话说清你要做什么

对这个项目的后端做一次**对抗性审查**：先用命令确认事实，再**尝试证伪**第 5 节列出的断言，最后按第 7 节的格式给出分级发现。

**你的价值在于找出真问题，不在于写综述。** 找不到问题时，说清"我验证了什么、怎么验证的、还有什么没验证"，比给一堆泛泛建议有用得多。

## 1. 作品是什么（30 秒）

- 参赛作品：粤港澳大湾区 AI Coding 创新大赛 · 方向二（AI + 学术科研助手）。
- 作品形态 = **一个 LearnBuddy 专家（AI 入口）+ 一个静态网页（使用入口）**，两者靠一份格式固定的结构化文件传递。
- 专家侧：把杂乱的实验记录（日志片段、周报、聊天描述）读成**带编号与原文证据的结构化档案**，并在入库当下反查同类尝试与冲突判断。
- 网页侧：承载经验库、检索、立项检查、条件对比矩阵、孵化清单、导入导出；**零模型调用**。
- 后端（本次审查对象）承载的是：契约与校验、库读写与去重、召回打分、评测跑批、导出、六个技能的确定性部分、以及随专家包分发的命令行引擎。

## 2. 硬约束（违反任一条即为严重问题，请优先核查）

1. **网页侧零模型调用**：AI 能力只能出现在专家侧（后端）。
2. **证据引用必须带档案编号 + 原文片段**（片段 ≥4 字符）；没有出处的判断不许出现在任何输出里。
3. **假设不得写成结论**：`attribution.type` 只能是 `observed`（日志里真的写了原因）或 `assumption`（推测）；日志没给原因时只能是后者。
4. **不引入第三方 AI / 云服务 / 新依赖**：后端只用 Python 标准库，不联网。
5. **确定性代码不得依赖运行时模型判断**：编号、去重、召回、门限、合并这类判定必须是纯函数 + 显式规则。
6. **库是 append-only 语义**：人工反驳不覆盖原判断，而是新增一条纠错档案。

## 3. 已知设计结论（**不要**把这些报成缺陷）

1. `src/rra/skills/*.py` 里的 `build()` 是 `raise NotImplementedError`——这是**设计结论**：平台上的技能脚本没有调用模型的能力（项目方用实物核对过平台内置脚本），语义判断由专家本身承担，代码只做确定性把关。详见 `reports/platform-boundary-probe-2026-09-19.md` 与 `docs/HANDOFF.md` 待办第 2 项。
2. 网页**不能**新增或编辑档案；两端目前靠**手动**导入/导出传递（平台侧自动数据通路未实测确认）。
3. 库内数据是**模拟数据**（`provenance.source = "模拟"`），原型不实现访问控制。
4. 不做向量检索与重排器（理由见 `docs/technical-notes.md`）。
5. 相似度计算只用于**检索召回**，语义判定在专家侧。
6. 语料里的阻塞点、硬件、精度等是**枚举维度**，不允许自由文本（这是刻意的契约约束）。
7. `avatars/` 只有 `.gitkeep`（头像未生成，官方校验与注册都不依赖它）。

## 6. 环境与命令（Windows 本机实测）

```text

node 22   ：%USERPROFILE%\.workbuddy\binaries\node\versions\22.22.2\node.exe
```

| 目的 | 命令 |
| --- | --- |
| 跑全部测试（Python + 前端） | `<py> run_tests.py`（node 路径可用环境变量 `RRA_NODE` 指定） |

注意事项（这些坑项目方都踩过）：

- 跑平台官方脚本（expert-manager 系列）前必须设 `PYTHONIOENCODING=utf-8`，否则 GBK 控制台会在打印 emoji 时崩。
- 若在 PowerShell 下取命令输出：**PowerShell 不回传 stdout**，请把输出重定向到文件再读，直接看会得到空。
- CLI 的机器可读输出一律是 JSON；**退出码非 0 表示拒绝**，不要绕过它继续流程。

## 7. 输出格式（必须遵守）

每条发现一段，字段缺一不可：

- **编号 / 严重级**：`P0 阻塞`（作品不成立或数据错误）/ `P1 重要`（逻辑或一致性缺陷）/ `P2 建议`（可读性、效率）
- **位置**：`文件:行号`（必须真实存在）
- **现象**：可复现的最小描述
- **复现**：**可直接粘贴运行的命令**，或最小输入 JSON
- **根因**：一句话
- **影响**：破坏了第 2 节哪条硬约束 / 影响哪个交付物
- **建议修法**：具体到函数与期望行为（不要写"重构一下"这类不可执行的建议）
- **置信度**：高 / 中 / 低；低置信度必须显式标注"待确认"

末尾必须另附三节：

1. **「我核对后认为站得住的断言」**：哪几条验证过、用什么方法验证的；
2. **「我无法验证的部分」**：缺什么环境/数据，写清楚；
3. **「我认为最该先修的 3 件事」**：按投入产出排序，并说明为什么是这 3 件。
