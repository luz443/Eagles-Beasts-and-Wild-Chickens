```

**③ 判定与依据（带档案编号 + 原文片段）**

- 「有效」侧 **R-004 · observation 原文**：「显存稳定在 21G，训练完成，loss 曲线与 batch=32 基本重合」
  **R-004 · conditions 原文**：`{"seq_len":"512","model":"Llama-3-8B","precision":"bf16","micro_batch":"4","batch":"32（等效）"}`

- **库内自带的差异登记**（不是我事后推的）—— **R-005 · links 原文**：
  `{"target":"R-004","relation":"相似","same":[{"dim":"model","value":"Llama-3-8B"}],
    "diff":[{"dim":"seq_len","from":"512","to":"4096"}],
    "transferable":"R-004 的做法只对激活主导的显存压力有效，对注意力矩阵开销无效"}`
  → 库自己就把这对判成 `相似`（**不是** `冲突`），并指明差异维度是 `seq_len`。
- CLI 确定性对比：`differing_dims: ["seq_len"]`、`verdict: "条件不同"`。

**差异维度（九维枚举名）**：**`seq_len`（序列长度）**，512 → 4096。
其余维度 `model` / `micro_batch` / `batch` 两侧取值相同。

**为什么判"条件不同"而非"真冲突"**：`bin/rra/skills/condition_compare.py` 规则原文「**任一维度不同即不得判为冲突**——条件不同时直接返回「条件不同」，不再交给结论比对」。`differing_dims` 非空 → 引擎直接裁定 `条件不同`。
**结论口径**：不是"梯度累积到底有没有用"的矛盾，而是**梯度累积的有效性随 `seq_len` 变化**：512 下有效（R-004），4096 下对激活主导的 OOM 无效（R-005）。R-005 的 blocker 原文也自述了方向「仍然 OOM；**累积并不能降低单步激活峰值**」。

**④ 结论：通过。**

{ "ok": true, "total": 15,
  "report": { "added": [],
              "duplicated": ["R-001","R-002","R-003","R-004","R-005","R-006","R-007","R-008",
                             "R-009","R-010","R-011","R-012","R-013","R-014","R-015"],
              "renumbered": {}, "violations": [] },
  "written": null,
  "note": "未传 --out，只报告合并结果，不写任何文件" }
```

**③ 判定与依据 —— 两条保证各自怎么落地**

**A. 去重命中如何被保证**
`merge-library` 对每条 incoming 记录算 `dedup_key` 再与库内已知键比对，命中即计入 `duplicated` **而不入库**（`bin/rra/library/store.py` 的 `merge()` 第一遍）。
指纹算法（`bin/rra/library/dedup.py` 的 `Deduplicator.key_of`）：**归一化（NFKC → 去标点 → 去全部空白 → 转小写）后的 `attempt` ␟ `blocker` ␟ `links` 的 same+diff 条件 ␟ `artifacts`**，若档案带 `conditions` 再追加排序后的第五段。源码注释原文：「其中条件与产物必须**排序后**参与，否则同样的两条档案只因条目顺序不同就会被判成不同」。
实测（把库自身当 incoming）：`duplicated` **精确列出全部 15 条**、`added: []`、`renumbered: {}` → **去重把 15 条全部拦下了**。

**B. 编号唯一连续如何被保证**
- 取号：`next-id` → `LibraryStore.next_id` → `"R-%03d" % (max_seq + 1)`；库内最大为 R-015 → **R-016**。`_max_seq` 对解析不出的脏编号**跳过**（源码注释原文「不因个别脏编号整体失败」）。
- 入库时的撞号处理：`merge()` 的重编号是**一次性**的 —— 先只对「会真正入库**且**撞号」的记录，从 `max(base ∪ incoming) + 1` 起依次分配新号并留下 old→new 映射，再统一改写引用；`_rewrite_refs` 会同步改写 `links[].target`、`evidence_refs[].record`、`resurrection.unblocks[].basis`，源码注释原文「重编号只改 `id` 是不够的……不改写就会「指向另一条记录」」；`provenance.remap_from` 记旧号且**不覆盖更早一跳**。
- **如实说明**：本轮库里没有撞号的新记录（`duplicated` 满 15、`renumbered: {}`），所以**重编号分支未被触发** —— 我不把"没触发"说成"验证过"。能确定性核对的是：`next-id` 给出 **R-016**，且 `merge-library` 输出 `violations: []`（**合并结果先过整库契约校验才允许写**）。

**C. 零写入的证据**
- 输出 `written: null` + note 原文「未传 --out，只报告合并结果，**不写任何文件**」。
- 源码落点：`cmd_merge_library` 中 `if args.out: LibraryStore(Path(args.out)).save(merged) else: result["written"] = None` → **只有显式给 `--out` 才写**，这是 CLI 文档承诺「默认只读」的实现。
