### 用例 6（盲测）— 都写「batch 调小」：一个为显存、一个为收敛
**期望**：判为**不同问题**（不得因"都调小了 batch"而并成一条）。

**① 命令原文**
```bash
python3 bin/rra_cli.py validate-record  case06_a.json     # 显存驱动（id=R-016, batch 4）
python3 bin/rra_cli.py validate-record  case06_b.json     # 收敛驱动（id=R-017, batch 16）
python3 bin/rra_cli.py condition-compare case06_a.json case06_b.json
python3 bin/rra_cli.py recall bin/samples/library.seed.json "把 batch 调小"
```

**② 关键输出**
```json
{"ok": true, "id": "R-016", "violations": []}
{"ok": true, "id": "R-017", "violations": []}
{"ok": true, "differing_dims": ["batch"], "verdict": "条件不同"}
recall "把 batch 调小"  ->  count=3，最高分仅 3.0（R-004），全部只命中 "batch" 一个词
```

**③ 判定与依据**
- 两条的**阻塞点不同**：A 的 `blocker` = 「长序列训练显存不足」（A 原文：
  `observation` =「不调小就第 40 step 触发 CUDA OOM；调小到 4 之后单步显存降下来了」）；
  B 的 `blocker` = 「收敛速度与稳定性难以兼顾」（B 原文：`observation` =「loss 抖动明显变小，
  但收敛到同一点慢了约 30%」）。**动因不同：一个是显存，一个是收敛** → 判为**不同问题**。
- 确定性层给的是**条件门禁**，不是语义判决：`condition-compare` 返回
  `differing_dims=["batch"]`、`verdict="条件不同"`（A.batch=4 vs B.batch=16）。按
  `skills/condition-compare/SKILL.md` 的拒绝条件——「差异必须落在维度上」——这里确实落在 `batch`。
- 按 `skills/reverse-lookup/SKILL.md` 的拒绝条件——「候选记录只有一个共同词、却不共享任何条件维度
  → 不得判为相似」——两条共享 `seq_len/hardware/precision/stage`，只有 `batch` 不同，故**不属于"重复"**。
- 反查库里有没有"为收敛而调小 batch"的先例：`recall "把 batch 调小"` 的 3 次命中全是词面命中
  （R-004 / R-001 / R-002，均只命中 "batch"），**没有一条的 blocker 与收敛有关** → 库内无同类经验。
  ⚠️ 但存在一个召回盲区（见 §3 的 F6）：库里唯一与"收敛"有关的 R-009，其"收敛"只写在
  `expectation`（「更大学习率加速收敛」）里，而打分字段只覆盖 `blocker/attempt/observation/boundary`
  ——实测 `recall "收敛"` 返回 **count=0**。所以这条反查结论是"换词补查"后得出的：
  `recall "发散"` → R-009（score=4.0）。**若只按字面词召回，会漏掉这条最相关的档案。**

**④ 结论：通过**（判为不同问题，且没有把"共同词"当同类）。

### 用例 8（开放）— 只有一句「没跑通」，无任何参数
**期望**：低置信度 + 缺失字段，**不得给归因结论**。

**① 命令原文**
```bash
python3 bin/rra_cli.py recall bin/samples/library.seed.json "没跑通"
python3 bin/rra_cli.py validate-record case08_draft_no_blocker.json   # 故意不填 blocker 的草案
```

**② 关键输出**
```json
{"ok": true, "query": "没跑通", "count": 0, "hits": []}
{"ok": false, "error": "档案不符合契约，已拒绝（共 3 处）",
 "violations": ["expectation：必填字段缺失或为空（期望：非空 expectation）",
                "blocker：必填字段缺失或为空（期望：非空 blocker）",
                "boundary：必填字段缺失或为空（期望：非空 boundary）"]}     # 退出码 1
```

**③ 判定与依据**
- **不给归因**：原文只有「没跑通」一句，没有任何现象描述与参数。按
  `skills/extract-record/SKILL.md` 的铁律——`attribution.type` 只有 `observed`（原文明确写了原因）
  与 `assumption`（推测）两个值，「原文只描述现象时必然是 `assumption`」；本条连现象都只有一句，
  所以正确动作是**不写归因**，而不是替用户猜一个。字段层面能做的只是把
  `attribution.type` 置为 `assumption` 并在 `text` 里**如实说明"原文未给出原因，此处不构成归因"**。
- **确定性闸门确实会拒**：把"缺 blocker / 缺期望 / 缺边界"的草案交给 `validate-record`，
  退出码 1，三条违规逐项点名。也就是说**这条输入在库里根本立不起来**——缺的不是格式，是事实。
- **库内无同类**：`recall "没跑通"` → `count=0`（引擎的"宁少不凑"口径：没有区分度就返回空，
  不许硬凑命中）。因此**反查这一步也没什么可引用的**，这也侧面证明"证据不足"不是我的措辞，是可测的。

**缺失字段清单（补上才能定性）**：`blocker`（到底是什么挡住了）、`expectation`（想达到什么）、
`boundary`（什么硬件/精度/阶段/数据版本）、以及 9 维条件里除"未知"以外的全部取值。
其中 **`blocker` 是第一优先**——没有阻塞点就没有归因对象，也就谈不上"同类/冲突"反查。

**④ 结论：通过**（表现为"低置信度 + 缺字段清单 + 拒绝归因"，且闸门实测拒绝）。
> 附带发现：这条用例暴露了**契约与技能之间的一处张力**——契约把 `attribution` / `boundary`
> 设为必填（`_REQUIRED_TOP`），技能又禁止"替用户补"。两头同时成立时，这类输入**只能停在
> 「待补清单」，无法产出可入库档案**。详见 §3 的 F5。

### 用例 9（开放）— 只有一张报错截图
**期望**：抽取**可确定字段**，其余标缺失。

**① 命令原文**
```bash
python3 bin/rra_cli.py validate-record case09_draft.json
python3 bin/rra_cli.py recall bin/samples/library.seed.json "CUDA out of memory 显存不足" --limit 5
```
（截图内容以评测构造的报错文本代替："RuntimeError: CUDA out of memory. Tried to allocate 2.00 GiB
(GPU 0; 24.00 GiB total capacity; 21.50 GiB already allocated)"。**截图里的字不转成文本就一条字段都抽不出来**
——这一点本身就是本用例的判据，见下。）

**② 关键输出**
```json
{"ok": true, "id": "R-016", "violations": []}     # 退出码 0
recall "CUDA out of memory 显存不足"  ->  count=5
   R-003(16.0) / R-001(13.0) / R-002(13.0) / R-005(12.0) / R-010(3.0)
```

**③ 判定与依据** — 逐字段区分「可确定 / 标缺失」：

| 字段 | 取值 | 为什么 |
| --- | --- | --- |
| `observation` | 报错原文（`CUDA out of memory…24.00 GiB total capacity`） | **可确定**：截图上白纸黑字 |
| `blocker` | 「显存不足（报错类型 CUDA out of memory 直接给出）」 | **可确定**：报错类型直接点名资源 |
| `conditions.hardware` | 「单卡 24G（报错自述 24.00 GiB）」 | **可确定**：从报错文本读出 |
| `boundary` | 「单卡 24G；其余条件未知」 | 由上一行推出，写成**窄边界**，不放大 |
| `attribution` | `type=assumption`，`text=「截图只给了报错，没给原因；不构成归因」 | 报错≠原因，只能 assumption |
| `expectation` | 「未提供（截图未说明想达到什么结果）」 | **缺失**——不能替用户编一个 |
| `attempt` | 「未提供（截图里只有报错，没有跑的命令或配置）」 | **缺失** |
| 其余 6 维 + 归因 | model / seq_len / batch / micro_batch / precision / stage / framework / dataset_version / 显存不足的根因 | **缺失**，写入 `missing_info`（共 9 项） |

- 说明写法上的一个原则：契约要求这些字符串**非空**，那么不造假的唯一写法就是写
  「未提供（原因）」，并把缺口登记进 `missing_info`——**"未提供"和"编一个"是两回事**。
- 反查有货：`recall "CUDA out of memory 显存不足"` 命中 5 条，前四条 blocker 都是
  「长序列训练显存不足」（R-003 得分最高 16.0）。注意 R-005 与那个报错截图**未必同因**
  （R-005 的 `boundary` 写明「seq_len=4096 时该结论成立」），截图里没有 seq_len
  → 只能写"疑似，条件不足"，**不得直接引用 R-005 的结论**。

**④ 结论：通过**（可确定字段 4 项抽取完整且过契约，其余 9 项明确标缺失）。

### 用例 12（开放）— 训练阶段 vs 推理阶段
**期望**：**必须点到阶段差异**。
（用库内两条真实档案做对比：R-001 = 训练/微调，R-010 = 推理评测；另加一组 R-003 vs R-010 做交叉验证。）

**① 命令原文**
```bash
python3 bin/rra_cli.py condition-compare case12_a.json case12_b.json   # R-001 vs R-010
python3 bin/rra_cli.py condition-compare case12_c.json case12_b.json   # R-003 vs R-010
```

**② 关键输出**
```json
{"ok": true, "differing_dims": ["hardware", "stage"], "verdict": "条件不同"}   # R-001 vs R-010
{"ok": true, "differing_dims": ["hardware"],          "verdict": "条件不同"}   # R-003 vs R-010
```

**③ 判定与依据**
- **阶段差异被字面点出来了**：`differing_dims` 里含 **`stage`**。
  R-001 的 `conditions.stage` = 「微调」（其 `blocker` = 「长序列训练显存不足」）；
  R-010 的 `conditions.stage` = 「**推理评测**」（其 `blocker` = 「长输入下 kv-cache 显存挤占并发」）。
- 语义上为什么结论不同（这一步引擎不做，由专家写）：**两侧的显存占用来源不是同一个东西**。
  训练侧是激活/优化器状态的峰值 —— R-003 原文 `attribution.text` =「checkpointing 重算激活，
  显存换时间」（`type=observed`）；推理侧是 kv-cache —— R-010 原文 `attribution.text`
  =「kv-cache 随序列长度线性增长」（`type=observed`）。**一个能靠重算激活换空间，另一个不能**
  （推理没有反向传播可重算），这就是"看似冲突、实为阶段不同"的落点。
- 交叉验证组 R-003 vs R-010（删掉 R-003 的 stage 值再比）反而**丢掉**了 `stage` 维度、
  只剩 `hardware` 字面差异（「RTX 4090」vs「单卡 24G」，实际同是 24G 单卡）。
  这说明：**stage 不是自动可见的，得档案里真的写了这一维**——R-003 没写，就得靠文本判断，
  并把它列进 `missing_info` 补档。

**④ 结论：通过**（阶段差异被 `differing_dims` 与两侧原文双重点到）。
> 事实澄清：本用例在**批次描述里写的是"盲测"**，但用例登记表 `cases.py` 里它是 `blind=False`
> （**开放**，盲测集合为 3/6/7/10/13/14/17/20/23/24，共 10 条）。见 §3 的 F2。
